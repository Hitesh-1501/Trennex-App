### Audit findings and access matrix

| Severity | Finding and evidence | B4 action |
| --- | --- | --- |
| High, confirmed | `firestore.rules` allowed a signed-in customer to create `/users/{uid}/orders/{id}` with arbitrary item price and `Pending` status. `UserRepository.saveOrder` no longer calls this path; the Android app only reads legacy orders and uses `createOrder` for new checkout. | Retained owner reads of old orders; denied customer create/update/delete. New orders remain server-created under `/orders`. |
| Medium, confirmed | `askShoppingAssistant` returned no-match results before the daily quota transaction, allowing unlimited no-match requests. | Count every authenticated valid question before catalog matching; added emulator quota test. |
| Medium, confirmed | Assistant upstream error bodies were copied into exception logs. A third-party body could include request text or other sensitive content. | Log a fixed code and discard the upstream body; return a generic callable error. |
| Medium, confirmed | `createOrder` accepted any nonempty `requestId` and coerced item quantities with `Number()`. A path-like ID could cause a Firestore path error, and malformed types could reach internal errors. | Require safe bounded IDs and numeric integer quantities; validate item, shipping, recipient and COD shapes before authoritative price/stock transaction. |
| Medium, confirmed | Storage accepted any `image/*` MIME type at arbitrary catalog/user subpaths; this included SVG and unsupported paths. | Permit bounded JPEG/PNG/WebP on existing catalog category/banner/product media paths and a private avatar path; retain default deny. |
| Low, confirmed | Profile, address, cart and checkout-request rules allowed missing or malformed values in several fields. | Add field/type/length/range checks while keeping Android's current writes and legacy reads. |
| Medium, confirmed | Product reads used a broad `active` flag and the legacy fallback accepted draft-like documents with legacy fields, allowing a `DRAFT` product carrying those fields to be read publicly. | Require `status=ACTIVE` for current products and no status/active markers for legacy fallback; keep tested legacy reads. |
| Potential, deferred | Existing admin claims can write broad catalog, inventory, order and audit documents; claim issuance/revocation and admin operation auditing need B5. Public `/appConfig/{id}` has no documented content allowlist. Profile contact fields are user-editable and must not be treated as verified identity. Storage checks metadata, not image bytes. | Document for B5/C/content review; do not claim these are presently exploitable without a trusted admin or a use of unverified profile data. |

| Data/path | Signed-out | Customer owner | Other customer | Admin claim |
| --- | --- | --- | --- | --- |
| Active/legacy public catalog and approved catalog media | Read | Read | Read | Read/write |
| Draft catalog, variants under draft parent, inventory/coupons | Deny | Deny | Deny | Read/write |

Item bundles hold product ID, optional variant ID/category, price, and quantity. COD `purchase` deliberately omits standard `value` so an unpaid order is not represented as collected revenue; `order_value` is a separate custom metric candidate.
- Purchase path: `createOrder` callable's server-confirmed order ID is retained. After checkout success, the client reads that order and its items from Firestore **server** source and validates owner, status, INR, COD, total, and item fields before logging. Analytics read failures cannot turn a confirmed order into a checkout failure; they may leave that purchase unreported. SharedPreferences reserves the order ID before event dispatch to prevent retries, rotation, repeated callbacks, or restart from emitting it twice. This favors at-most-once reporting over guaranteed delivery.
- Privacy: the tracker rejects unknown event names/parameter keys and invalid values. It never sends names, email, phone, OTP, addresses, tokens, payment details, raw AI prompts/responses, or raw search queries. Cart events run after local mutation success, preserving the existing durable offline sync. Screen/list/search guards avoid repeat emissions from ordinary state collection. The Analytics preference is device-level, persists across sign-in changes, and can be turned off from Profile.
